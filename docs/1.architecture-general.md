# App Lab General Architecture

App Lab is a browser application for creating, editing, running, exporting, sharing, and syncing small sandboxed
HTML/CSS/JavaScript apps.
The host shell is React and TypeScript. User-created apps run as complete HTML documents inside sandboxed iframes.

The central architectural rule is separation of responsibility:

- `src/core` owns local app records, local app data, JSON validation, and browser persistence.
- `src/runtime` owns the iframe boundary and the `window.AppLab` API exposed to generated apps.
- `src/sync` owns provider-neutral sync primitives and provider adapters.
- `src/ui` owns the React workspace shell, tool panels, dialogs, and user workflows.

## Product Model

The user sees App Lab as a workspace:

- the launcher lists apps
- an app opens as the main surface
- Source edits the app document
- Console shows iframe logs/errors
- BuilderAI currently provides a prompt+code handoff while the actual agent loop is still being built
- Settings configures AI and storage/sync, including Firebase setup and whole-workspace device sync

Generated apps should feel like user-owned local tools, not pages inside a developer console. The shell should stay quiet and
predictable around the app, with controls available when needed but not taking over the experience.

## Core

`src/core` is headless browser-bound logic. It must not import React or render UI.

Responsibilities:

- create, list, read, update, and delete app records
- read and write per-app JSON data
- derive launcher title/description from source HTML metadata
- normalize and size-limit generated app data
- persist local state in IndexedDB
- provide in-memory implementations for tests
- expose explicit service methods to UI/runtime/sync

The current IndexedDB database name is `app-lab-v2`. This remains intentional until there is a deliberate migration.

Core rules:

- generated app source is stored as data, not executed by core
- generated app data must be JSON-compatible
- app records and app data are addressed by explicit app ids
- app metadata is read from the HTML `<head>` when source is created or saved
- if a feature needs remote sync, core should expose enough local state for sync but should not contain provider-specific code

App metadata source of truth:

- title: `<title>App name</title>`
- description: `<meta name="description" content="...">`
- missing title falls back to the existing app name, then `Untitled App`
- missing description falls back to the existing app description, then an empty string

The launcher app actions dialog is intentionally basic. It can delete an app, but title/description edits should happen by editing
the source HTML head.

## Runtime

`src/runtime` owns the sandboxed iframe boundary.

Responsibilities:

- prepare generated app HTML before loading it into the iframe
- inject the app CSP
- inject host-compiled app CSS when the source opted into Tailwind
- inject a per-load runtime capability
- inject `window.AppLab`
- inject a pinned Alpine.js runtime before generated app code and start it after the app body is parsed
- validate app-to-host messages
- route app data requests through the host
- forward console output to the host Console tool
- recover from unexpected iframe navigation

Runtime security posture:

- iframe uses `sandbox="allow-scripts"` without `allow-same-origin`
- generated app CSP blocks network, remote resources, forms, frames, workers, objects, and base URL rewriting
- Alpine-enabled generated apps allow `unsafe-eval`, because normal Alpine expressions rely on dynamic evaluation.
- The host CSP also includes `unsafe-eval` as the browser-level ceiling for local iframe documents. Local documents such as
  `srcdoc` cannot loosen a stricter parent `script-src`; the React host does not use eval, and the per-app CSP can still tighten
  this for a future vanilla runtime mode.
- app RPC is scoped to the active app and per-load iframe capability
- generated apps should use `AppLab.getData()`, `AppLab.saveData()`, `AppLab.onDataChange()`, and `AppLab.onError()`
- generated apps may opt into host-compiled Tailwind with `<meta name="app-lab-tailwind" content="enabled">`
- generated apps must not include Tailwind scripts, imports, CDNs, or package-manager syntax
- Tailwind utility classes should appear literally in `class` attributes when possible, because App Lab compiles static CSS from
  source on save/create and injects that CSS into the sandbox
- generated apps may use the host-injected Alpine runtime, but should not include external Alpine scripts, imports, or CDNs
- generated apps may use normal Alpine expressions such as `x-model`, `x-show="tab === 'main'"`, ternary `:class` values, and
  method calls
- non-trivial generated apps should register components with `Alpine.data(...)` and use `x-data="componentName"`
- generated apps should save JSON snapshots through `AppLab.saveData(...)`, not DOM nodes, Events, Maps, Sets, functions, or other
  non-JSON objects
- the sandbox document builder has a `vanilla` runtime mode that skips Alpine and keeps `unsafe-eval` disabled. The product UI does
  not expose this yet, but the runtime boundary is prepared for a future per-app vanilla/Alpine choice.

Important limitation:

Generated app code can read its own app data through `AppLab.getData()`. App Lab protects the host, other apps, and host secrets,
but it does not prove that arbitrary generated code cannot disclose its own app-owned data. Users should only run/share apps from
sources they trust.

## UI

`src/ui` is the React view layer. Styling uses Tailwind CSS.

Primary surfaces:

- launcher
- active app viewport
- Source tool
- Console tool
- BuilderAI tool
- Settings

The settings experience is split by concern:

- AI settings contains OpenRouter/model configuration
- Storage and sync contains first-time Firebase setup and whole-workspace device sync
- Firebase setup is a guided checklist: create Firebase resources, enable Anonymous Auth and publish rules, then paste config
- Sync device is for moving the whole workspace to another browser; it is not the same as importing a single app invite

The launcher should show app relationship and sync health separately:

- Private
- Shared by me
- Shared with me
- Cloud health: synced, pending/syncing, offline, or needs attention

## Source Workflow

The Source tool edits the complete HTML document for the active app. Saving source updates the local app record, refreshes
launcher metadata from the HTML head, and reloads the sandbox.

If the source includes the App Lab Tailwind marker, the React shell compiles Tailwind utility classes into static CSS before saving
the app record. The source remains compact; the derived `compiledCss` is stored alongside the app source and injected into the
sandbox at runtime.

For synced apps, source saves also update the source room. Remote source updates reload the sandbox for the active app; remote
data updates can be handled in-place with `AppLab.onDataChange`.

The Source tool can export source as `.html` and app data as `.data.json`, and it also offers clipboard fallbacks. Import is not a
first-class UI workflow yet.

The BuilderAI prompt+code helper is a supported external-LLM workflow. The prompt should teach generated apps to:

- use `AppLab.getData()` and `AppLab.saveData()`
- use the App Lab Tailwind marker and literal Tailwind classes for compact styling
- use host-injected Alpine where it simplifies UI state
- separate persisted app data from transient UI state
- listen for remote data changes when the API is available
- avoid full UI resets on data changes
- report visible errors

## Testing

Build verification:

```bash
pnpm typecheck
pnpm test
pnpm build
```

Test scope should grow with the feature:

- core tests for app records and JSON persistence
- runtime tests for iframe capabilities, navigation recovery, console forwarding, and app data RPC
- sync tests for crypto, provider contracts, room metadata, conflict behavior, and invite parsing
- UI tests for critical flows such as metadata parsing, export, settings, and sync status
- Playwright tests for local persistence and Firebase-backed sharing/sync regressions
