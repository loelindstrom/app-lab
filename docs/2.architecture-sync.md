# App Lab Sync Architecture

This document defines the target sync behavior for App Lab. It is intentionally more detailed than the general architecture
document because sync affects storage, runtime APIs, sharing, security, and user expectations.

The Firebase experiment is stashed as `firebase-sync-experiment-reference`. It proved that encrypted rooms and live Firebase
updates can work, but it also showed that the product model needs to be clearer before implementation continues.

## Goals

Sync should support:

- automatic encrypted backup for apps owned by the user
- restoring the user's workspace on another device
- live shared apps with friends
- clear ownership and sharing state in the launcher
- provider-neutral sync internals
- future provider adapters beyond Firebase
- future stronger sharing permissions without redesigning app records

Sync should not require:

- every collaborator to create a storage-provider account
- generated apps to know provider details
- users to understand rooms, manifests, or encryption keys during normal use

## Non-Goals For The First Robust Version

These are explicitly not first-version requirements:

- per-collaborator read-only/write-only enforcement
- revocation that forcibly removes already-shared secrets from other devices
- server-side source review
- perfect automatic merge for arbitrary generated app JSON
- preventing a malicious generated app from disclosing its own app data

## Vocabulary

Storage profile:

The user's configured remote storage provider. The first likely provider is Firebase Realtime Database, but the sync engine should
only depend on a provider interface.

Owned app:

An app created by this workspace. If a storage profile is configured, owned apps are automatically backed up to the user's storage
profile.

Joined app:

An app imported from someone else's invite link. It keeps pointing at the owner's rooms/provider. It is not automatically mirrored
into the recipient's storage profile.

Private copy:

A fork of any app into the current user's workspace and storage profile. A private copy no longer follows the original shared app.

Workspace manifest:

Encrypted remote record that describes the user's workspace: owned apps, joined apps, room references, local display metadata, and
last-seen versions.

Source room:

Encrypted remote room containing app source and app metadata.

Data room:

Encrypted remote room containing app-owned JSON data.

Room reference:

The local metadata needed to load/decrypt/sync a room: provider id/config reference, room id, decrypt secret, last-seen version,
and future access mode.

## User-Facing Model

The user should not need a separate "Sync workspace" button in the launcher.

Preferred model:

- if no storage profile exists, apps are local only
- when the user configures storage, App Lab backs up owned apps automatically
- new owned apps get source/data rooms automatically
- restoring another device is done from Settings, Storage and sync
- sharing an app reveals an invite to existing rooms; it does not create new rooms every time

Settings should contain:

- AI settings
- Storage and sync

Storage and sync should contain tabs or sections:

- First-time setup
- Restore another device
- Advanced provider details

The first-time setup should explain:

- create/configure provider
- paste provider config
- publish provider rules if needed
- App Lab will encrypt payloads before upload
- owned apps will be backed up automatically

Restore another device should explain:

- open App Lab on the new device
- paste/import workspace recovery material
- App Lab loads the encrypted workspace manifest
- owned and joined apps appear in the launcher

## Local App States

Launcher should clearly distinguish:

- Local only: no remote rooms
- Backed up: owned app with remote rooms
- Shared by me: owned app with invite-capable rooms
- Shared with me: joined app using another user's rooms
- Private copy: forked local/owned copy of a previous shared app
- Needs attention: conflict, missing room, provider error, or source update pending

This display matters because user expectations differ:

- deleting a local-only app removes it from this browser
- deleting a joined app leaves the shared room untouched
- deleting an owned shared app may affect collaborators
- copying a joined app creates new rooms only if the user has a storage profile

## Room Creation

Owned apps should get remote rooms automatically when storage is configured.

Rules:

- creating a new app while storage is configured creates source and data rooms
- enabling storage for an existing local workspace offers to back up all local apps
- repeated "Share" does not create rooms
- Share only reveals or copies an invite to existing rooms
- if an owned app has no rooms because sync was disabled, Share first creates the rooms, then shows the invite

The experiment showed why this matters: creating new rooms on repeated Share splits sync state and can leave the owner writing to a
different room than collaborators.

## Invite Links

Invite links are bearer capabilities. Anyone with the link can join the shared app in the first robust version.

Invite material should be placed in the URL fragment (`#...`) so it is not sent to the hosting server in the HTTP request path.
Fragments are still sensitive because users can copy, screenshot, or paste them elsewhere.

Opening an invite:

1. App Lab detects the invite fragment on page load or `hashchange`.
2. App Lab loads and decrypts enough source metadata to show an import confirmation.
3. The user sees that this is a full collaboration app.
4. The user explicitly imports or cancels.
5. Import adds a joined app to the workspace.
6. The URL fragment is cleared after import/cancel.

Pasting an invite into the address bar while App Lab is already open must work.

## Joined Apps And User Storage

If a user imports a joined app and also has their own storage profile, App Lab must not automatically back up that joined app into
the user's storage provider.

Joined app source of truth:

- original provider
- original source room
- original data room

The user's workspace manifest may include the joined app reference so it appears on their other devices, but the app's source/data
rooms remain the original rooms.

If the user wants their own independent copy:

- provide "Make private copy"
- create new source/data rooms in the user's storage profile
- copy current source/data into those rooms
- mark the result as owned/private copy
- stop following the original shared app

## Share Button Behavior

Owner:

- Share shows/copies the existing invite
- if no rooms exist, Share creates rooms first
- future UI can show "Manage sharing"

Joined collaborator:

- technically, bearer links can be forwarded
- hiding Share does not prevent manual forwarding
- UI should avoid implying authority the user does not have
- recommended label: "Copy invite" or "Shared app details" instead of "Manage sharing"

## Delete Behavior

Local-only app:

- Delete removes local app record and local app data.

Backed-up owned app:

- Default action should be "Remove from this device" or "Delete app".
- If remote deletion is supported, make it explicit: "Delete from all synced devices".
- Remote delete should tombstone the room/manifest entry rather than silently disappearing.

Shared by me:

- Owner deletion needs a confirmation that collaborators may lose access.
- Prefer a remote tombstone record over hard delete so collaborators can show a clear state.
- Collaborators should see: "This shared app is no longer available."
- They can remove it or make a private copy if they still have cached source/data.

Shared with me:

- Delete removes the local/joined workspace entry only.
- It does not delete the original rooms.
- It does not affect other collaborators.

## Source Sync Behavior

Source code changes are different from app data changes because source updates can change executable code.

Rules:

- local source edits save to the source room for owned/shared apps
- remote source updates should not interrupt an actively running app without a visible boundary
- if app is inactive, App Lab should notify that a newer source version is available, but should not auto-apply it
- if app is active, App Lab should show "Source update available" with Reload/Apply
- reloading source reloads the iframe
- source update prompts should mention that trusted collaborators can publish code for this shared app

This avoids the app unexpectedly resetting while the user is in the middle of an interaction.

## Data Sync Behavior

Data updates should not reload the iframe.

Runtime API target:

```js
const data = await AppLab.getData(defaultValue);

AppLab.onDataChange((nextData, info) => {
  // Update persisted data model in-place.
  // Preserve transient UI state such as active tab, scroll position, modal state, and form focus.
});
```

Generated apps should keep two kinds of state:

- persisted data: the JSON that is synced
- view state: active tab, open dialog, selected item, scroll position, draft input, focus

Remote data changes update persisted data only. They should not reset view state.

If an app does not register `onDataChange`, fallback behavior can be:

- update host-side data cache
- show a small "Remote data changed" indicator
- allow user/app to reload manually

Avoid full iframe reloads for data-only updates.

## Conflict Behavior

The sync engine cannot safely merge arbitrary generated app JSON.

Default save model:

1. app reads data at version `N`
2. app saves a new JSON document based on version `N`
3. provider accepts only if remote version is still `N`
4. if remote version changed, save is rejected as a conflict

Default conflict response:

- fetch latest remote data
- notify the app via save error and/or future conflict callback
- do not silently overwrite remote data
- do not silently discard local user action

Generated app guidance should encourage operation-aware saves:

- for counters, append or apply an operation to latest state
- for lists, use stable ids
- for forms, save specific record edits
- avoid replacing the entire app state with stale local copies after a remote update

Future runtime API could support operation-shaped updates:

```js
await AppLab.updateData({
  op: "append",
  path: ["items"],
  value: newItem
});
```

The host could apply known operations against the latest known data and retry on version conflict. This would be safer than
generated apps manually doing get/modify/save, but it needs a deliberate operation format.

## Provider Contract

Provider-neutral room API:

```ts
interface SyncProvider {
  createRoom(input: CreateRoomInput): Promise<RemoteRoomSnapshot>;
  loadRoom(input: LoadRoomInput): Promise<RemoteRoomSnapshot>;
  saveRoom(input: SaveRoomInput): Promise<RemoteRoomSnapshot>;
}

interface RealtimeSyncProvider extends SyncProvider {
  subscribeRoom(input: SubscribeRoomInput): () => void;
}
```

Every provider adapter must support:

- high-entropy room ids
- exact room load
- version-checked save
- realtime or poll-based change detection
- shape validation
- no list-all-rooms behavior for invite users when provider rules can prevent it

Firebase Realtime Database is still a reasonable first provider, but it should be used behind this adapter.

## Data Model Sketch

Local app record:

```ts
interface LocalAppRecord {
  appId: string;
  name: string;
  description: string;
  sourceCode: string;
  createdAt: string;
  updatedAt: string;
  sync?: LocalAppSync;
}

type LocalAppSync =
  | OwnedAppSync
  | JoinedAppSync
  | PrivateCopySync;
```

Owned app sync:

```ts
interface OwnedAppSync {
  kind: "owned";
  storageProfileId: string;
  sourceRoom: RoomReference;
  dataRoom: RoomReference;
  shareState: "private" | "invite-created";
}
```

Joined app sync:

```ts
interface JoinedAppSync {
  kind: "joined";
  sourceProvider: ProviderReference;
  sourceRoom: RoomReference;
  dataRoom: RoomReference;
  importedAt: string;
}
```

Room reference:

```ts
interface RoomReference {
  roomId: string;
  decryptSecret: string;
  lastSeenVersion: number;
  accessMode: "full";
}
```

Workspace manifest:

```ts
interface WorkspaceManifest {
  schemaVersion: number;
  workspaceId: string;
  apps: WorkspaceManifestApp[];
  deletedApps: WorkspaceTombstone[];
  updatedAt: string;
}
```

The exact TypeScript should evolve during implementation, but these distinctions should remain:

- app ownership is explicit
- joined apps keep original provider references
- room references are not recreated by Share
- private copies have new owned room references

## Encryption And Integrity

The provider stores encrypted payloads only.

Room payload encryption should use AEAD. Associated data should include:

- room id
- room type
- schema version
- room version

Room types:

- workspace manifest
- app package/source
- app data

Clients reject:

- malformed envelopes
- authentication failures
- wrong room type
- snapshots older than the locally remembered last-seen version

Fresh restore limitation:

On a brand-new device, there is no prior local last-seen version. The client can authenticate the payload but cannot prove the
provider did not return an older valid snapshot. This is accepted initially and should be documented.

## Workspace Manifest

The workspace manifest is the key to cross-device sync.

It should include:

- workspace schema version
- storage profile reference
- owned app entries
- joined app entries
- local display ordering
- room references
- last-seen versions
- deleted/tombstoned app markers

The workspace recovery material should include:

- provider information needed to load the manifest
- manifest room id
- manifest decrypt secret

It should not be logged or placed in query parameters.

## Storage Profile Setup UX

Storage setup should not feel like developer infrastructure.

Recommended settings layout:

- Settings menu
  - AI
  - Storage and sync

Storage and sync:

- First-time setup
  - explain provider choice
  - paste provider config
  - provider-specific rule instructions
  - test connection
  - enable automatic backup
- Restore another device
  - paste recovery material
  - show workspace preview
  - import
- Advanced
  - room root path
  - provider rules
  - export recovery material

When storage is configured successfully, launcher should stop showing "Sync workspace" as a separate primary action. Sync is just
part of the workspace.

## Implementation Phases

Phase 1: storage profile and automatic owned-app backup

- add storage profile model
- add clean Storage and sync settings UI
- create workspace manifest room
- back up existing local apps on explicit enable
- automatically create source/data rooms for new owned apps
- launcher shows Local only / Backed up

Phase 2: invite import and joined app model

- Share reveals existing invite for backed-up owned apps
- Share creates rooms only for unsynced owned apps
- import confirmation creates joined app records
- joined apps keep original provider references
- joined app delete is local only
- launcher shows Shared by me / Shared with me

Phase 3: data sync without iframe reload

- add `AppLab.onDataChange`
- host pushes remote data changes into active iframe
- generated app prompt teaches data/view-state separation
- if no handler exists, host shows "Remote data changed" instead of reloading

Phase 4: conflict behavior

- host tracks base/last-seen data versions
- save conflicts return explicit errors
- prompt teaches generated apps to handle conflicts
- consider `AppLab.updateData` for safer operation-style updates after `onDataChange` is proven

Phase 5: source update boundaries

- remote source update is staged while app is active
- inactive apps show newer source available instead of auto-applying
- active apps show "Source update available"
- applying source update reloads iframe

Phase 6: workspace restore

- export recovery material as text, QR code, and downloadable file
- restore manifest on new device
- import owned and joined apps from manifest
- test fresh restore limitation and rollback checks

Phase 7: deletion, tombstones, and private copies

- owner delete writes tombstone
- joined missing-room handling
- make private copy flow
- future unshare/rotation design

## Generated App Prompt Requirements

The app-building prompt should teach models:

- persisted data is not UI state
- preserve active tabs, scroll, focus, and open dialogs when data changes
- register `AppLab.onDataChange` if available
- use stable ids for records
- keep schema versions and migrations
- handle save errors visibly
- debounce high-frequency saves
- avoid full rerenders that recreate the whole DOM unnecessarily
- for collaborative data, prefer operation-like updates where possible

This is necessary because sync quality depends partly on generated app structure.

## Scenarios

User enables storage for first time:

- App Lab validates provider config.
- App Lab creates workspace manifest room.
- App Lab creates source/data rooms for owned local apps.
- App Lab saves room references locally and remotely.
- Launcher marks apps as backed up.

User creates a new app after storage setup:

- App is created locally.
- Source/data rooms are created automatically.
- Workspace manifest is updated.
- App shows as backed up.

User opens App Lab on second device:

- User opens Storage and sync, Restore another device.
- User pastes recovery material.
- App Lab loads encrypted manifest.
- Owned apps and joined apps appear.
- Joined apps continue pointing at their original provider/rooms.

Owner shares an app:

- If rooms already exist, Share shows existing invite.
- If rooms do not exist, rooms are created first.
- Invite contains room references and decrypt material in fragment.

Collaborator imports invite:

- App Lab shows confirmation.
- User imports.
- Joined app appears in launcher as Shared with me.
- App data updates live without iframe reload.

Collaborator deletes joined app:

- Local workspace entry is removed.
- Remote rooms are untouched.
- Other collaborators are unaffected.

Owner deletes shared app:

- UI asks whether to remove locally or delete shared app for everyone.
- Delete-for-everyone writes a tombstone.
- Collaborators see unavailable/tombstoned state.

Collaborator has own storage profile:

- Imported app is still joined and points to original rooms.
- Own storage profile may store the workspace manifest entry.
- It does not mirror source/data rooms unless user explicitly makes a private copy.

Remote data changes while app is open:

- Host receives room update.
- Host decrypts and updates data cache.
- Host sends `onDataChange` to iframe.
- Generated app updates data model while preserving view state.

Remote source changes while app is open:

- Host receives room update.
- Host marks source update pending.
- User can apply/reload when ready.

Remote source changes while app is inactive:

- Host receives room update.
- Host marks source update pending.
- Launcher or app chrome shows that a newer source version is available.
- User can fetch/apply it later.
- App Lab does not silently replace runnable source.

Save conflict:

- Provider rejects save because expected version is stale.
- Host fetches latest remote state.
- App/user is notified.
- No silent overwrite.

Remote room missing:

- Joined app shows "shared app unavailable."
- User can remove local entry or make private copy from cached source/data if available.

## Resolved V1 Decisions

Source updates:

- Remote source updates do not auto-apply, even when the app is inactive.
- App Lab notifies the user that a newer source version can be fetched/applied.

Deletion:

- Owner delete creates tombstones when remote deletion is supported.
- Tombstones let collaborators see that the shared app was intentionally deleted instead of silently failing to load.

Forwarding shared apps:

- Joined apps may expose a Share/Copy invite action.
- The UI should still distinguish this from owner-level sharing management.

Unavailable shared apps:

- Keep cached source and cached data locally.
- The user decides whether to delete the joined entry or make a private copy from the cache.

Recovery material:

- Support text key, QR code, and downloadable file.
- Every export flow should warn that recovery material can restore the full workspace, including private apps and shared room
  memberships.

## Runtime Sync API Choice

The first generated-app sync API should start with `AppLab.onDataChange`.

`onDataChange` means:

- the host tells the app "remote data changed"
- the app receives the full latest data object
- the app updates its own in-memory model and UI
- the app is responsible for preserving active tab, scroll, focus, open dialogs, and draft inputs

`updateData` would mean:

- the app sends an update function or operation to the host
- the host loads the latest known data, applies the update, and saves with version checks
- the API can reduce lost-update bugs for common operations such as append, rename, increment, or delete
- the API needs more careful design because functions cannot be safely passed through postMessage, so it likely needs an operation
  format rather than a literal callback

V1 should implement `onDataChange` first because it directly solves the "remote update should not reload the iframe" problem. After
that behavior works, `updateData` can be designed as a safer write API for collaborative apps.
